## التحقق

نجح restore للحل من ذاكرة NuGet المحلية، ونجح بناء Release وتشغيل الاختبارات باستخدام:
`dotnet test SourcingTenderSystem/SourcingTenderSystem.slnx --no-restore -c Release -p:UseAppHost=false`.
النتيجة النهائية: **16 نجح، 0 فشل**. شملت عشر حالات لاختبار قرار سياسة المستند باستخدام مدخلات اصطناعية، وطلبَي HTTP مجهولين للتنزيل والمعاينة، ورفض JPEG في المسارين، وفحص تحدّي Passkey، وفحص الإعداد والملفات. لم تكن هناك مجموعة اختبارات سابقة ضمن الحل. بناء Debug الاعتيادي تعذّر بسبب قفل ملف التطبيق المشغّل؛ بناء Release لم يحتج إيقافه. بقيت التحذيرات السابقة في أسماء الترحيل وAiReport.

اختبار إضافي نجح عبر HTTP مع LocalDB اصطناعي: كلمة مرور صحيحة وصلت إلى إعداد Passkey، ولم يسمح رمز الوجه القديم بدخول لوحة المدير. اختبار Passkey حقيقي بجهاز أو authenticator افتراضي: NOT EXECUTED. اختبار تنزيل مصرح به عبر HTTP بصفوف تكليف SQL وملف فعلي، واختبار عبر معرف عطاء مختلف على مستوى الاستعلام: NOT EXECUTED؛ قرار السياسة المغطى لا يثبت تكامل استعلام SQL. لا استدعاء لمزود الوجه أو اختبار حيوية فعلي.

## إجراءات النشر

1. دوّر مفتاح Face++ من حساب المؤسسة المخوّل وأبطل القيم السابقة. راجع استخدام المفاتيح بعد التعرض. لا تضع المهام أو القيم الجديدة في المستودع.
2. عند تكامل مزود حيوية معتمد مستقبلاً، استخدم الأسرار البيئية أو User Secrets محلياً، مثل مفاتيح الإعداد `FacePlusPlus__ApiKey` و`FacePlusPlus__ApiSecret` إذا كان المحوّل المعتمد يستخدمهما. القيم الجديدة لا تعيد تشغيل مسار JPEG. [FaceID Pro H5 Lite](https://global.faceid.com/faceid-doc/docs/PRO-H5-Lite-GetToken.html) منتج منفصل عن Detect/Compare.
3. استبدل حزمة النشر ونظف الصور القديمة في المجلدات العامة والـCDN والنسخ المصدرة بموجب سياسة الاحتفاظ. إن وجب حفظ بيانات بيومترية، اجعلها مشفّرة خارج web root وبصلاحيات حساب الخدمة فقط؛ احذف القديم وفق السياسة، لا بنقل تلقائي أو تعديل قاعدة الإنتاج. عالج تاريخ Git فقط بتفويض صريح.
4. بعد النشر يلزم إعادة تسجيل الدخول؛ الحساب الذي كان يعتمد على الوجه فقط يستخدم كلمة مروره ثم يسجل Passkey. لا تعِد تفعيل الوجه قبل تحقق خادمي من تحدٍّ مؤقت ومربوط بالمستخدم، واختبارات الصور الثابتة والتكرار والنجاح الحقيقي.
